# Git: Pull Request и GitHub Actions

Учебный пример для DBA SRE. Всё выполняется в GitHub, без ВМ, PostgreSQL,
SSH-ключей, токенов и сторонних Python-пакетов.

## Что проверяем

В `config.ini` два вымышленных профиля хостов:

| Профиль | Учебный хост | Допустимый max_connections | Исходное значение |
| --- | --- | --- | --- |
| small | db01 | от 1 до 100 | 80 |
| large | db02 | от 1 до 300 | 150 |

Это условная политика упражнения, а не рекомендации по настройке PostgreSQL.
Профили и ограничения явно заданы в `check_config.py`, реальные ресурсы серверов
не измеряются. Файл никуда не доставляется и не применяется к БД.

## Демонстрация

1. Откройте `config.ini` и предложите изменение в новой ветке: 200 для обоих профилей.
2. Создайте Pull Request в `main`. Во вкладке Checks найдите `config-check`.
3. Посмотрите журнал: для db01 значение 200 превышает лимит 100,
   а для db02 то же значение допустимо.
4. В той же ветке исправьте small на 100, оставьте large равным 200.
5. Отправьте новый коммит. Проверка автоматически повторится в том же PR.
6. После успешной проверки прочитайте Files changed и завершите учебный PR.

Задание и пояснения преподаватель выдаёт отдельно.

## Как это работает

- `config.ini` содержит предлагаемую конфигурацию.
- `check_config.py` проверяет значения, обязательные профили и опечатки в ключах.
  Код завершения 0 означает успех, 1 означает ошибку.
- `test_check_config.py` проверяет сам проверяющий скрипт на корректных
  и некорректных примерах. Успешные тесты скрипта не означают, что `config.ini` допустим:
  проверка текущего файла выполняется следующим отдельным шагом.
- `.github/workflows/config-check.yml` запускает эти команды на исполнителе GitHub
  при создании/обновлении PR в main, при изменении main и по ручному запросу.

При желании те же проверки можно выполнить локально с Python 3:

```bash
python3 -m unittest -v
python3 check_config.py
```

## Границы примера

Красная проверка не запрещает создать PR. Для блокировки его слияния нужна
защита main с обязательной проверкой `config-check`. Без такого правила
красная отметка сама по себе не является запретом. Учитывайте права обхода правил.

Автор может менять и конфигурацию, и проверяющий код. Поэтому ревью включает
весь diff, особенно workflow и правила проверки. Это учебная автоматизация,
а не независимая система контроля или доказательство безопасности для любой нагрузки.

Здесь нет независимого одобрения, если автор сам открывает и сливает свой PR.
На занятии это допустимо для показа механики. Для совместной работы нужен другой ревьюер.

Не публикуйте в этом репозитории рабочие конфигурации, адреса и секреты.
Не добавляйте доступ к ВМ или self-hosted runner для запуска кода из PR.
Изменение реального max_connections требует перезапуска PostgreSQL;
этот пример ничего не меняет в работающем кластере.
