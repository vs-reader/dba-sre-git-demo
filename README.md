# Проверка конфигурации перед слиянием

В этом репозитории разбираем обычную задачу администратора: изменить настройку,
показать её коллеге и проверить до включения в общую версию.

Для примера взяли `max_connections`. В `config.ini` есть два учебных профиля:
`small` для db01 и `large` для db02. Для первого установили предел 100 подключений,
для второго — 300. Исходные значения — 80 и 150.

Попробуем поставить 200 для обоих профилей. Для large это допустимо,
для small — нет. GitHub Actions обнаружит ошибку и покажет, какое правило нарушено.
Затем исправим настройку в той же ветке и увидим повторную проверку.

Лимиты придуманы для упражнения. Это не рекомендации по настройке PostgreSQL.
К реальным серверам пример не подключается.

## Что находится в репозитории

- `config.ini` — настройки, которые будем менять.
- `check_config.py` — проверка значений по правилам каждого профиля.
- `test_check_config.py` — тесты самого проверяющего скрипта.
- `.github/workflows/config-check.yml` — когда и как запускать проверки в GitHub.

## Git и Pull Request

Git создаёт коммиты, управляет ветками и передаёт их между репозиториями.
Pull Request — возможность GitHub, а не отдельная команда Git.
В Bitbucket есть аналогичный механизм, но команды `gh` работают именно с GitHub.

Последовательность такая: создаём локальную ветку, делаем коммит,
публикуем ветку через `git push`, затем открываем PR с предложением
слить эту ветку в `main`.

Всё это можно сделать из терминала. Для работы с файлами и ветками используем
`git`, для создания PR и просмотра проверок — GitHub CLI, команду `gh`.
Вместо `gh` можно использовать веб-интерфейс или API GitHub.

## Пример из терминала

Для этих действий нужны Git, GitHub CLI и право записи в репозиторий.
Если повторяете пример в своём fork, замените адрес репозитория на свой.
При создании PR укажите свой репозиторий через `--repo YOUR_LOGIN/dba-sre-git-demo`,
если GitHub CLI предлагает отправить PR в исходный репозиторий преподавателя.

### 1. Подготовить локальную копию

Если GitHub CLI ещё не авторизован:

```bash
gh auth login --hostname github.com --git-protocol https --web
```

Скопируйте репозиторий в свободный каталог:

```bash
git clone https://github.com/vs-reader/dba-sre-git-demo.git
cd dba-sre-git-demo
git switch main
git pull --ff-only
git switch -c demo/connections-cli
```

Если копия уже есть, повторный clone не нужен. Сначала проверьте
`git status` и сохраните свою незавершённую работу.
Если имя ветки уже занято, выберите новое.

### 2. Изменить конфигурацию и создать коммит

Откройте `config.ini` в редакторе и задайте:

```ini
[small]
max_connections = 200

[large]
max_connections = 200
```

Посмотрите разницу, подготовьте файл и сохраните изменение:

```bash
git diff
git add config.ini
git diff --staged
git commit -m "Set connection limit to 200 for both profiles"
```

Коммит пока существует только в локальном репозитории.

### 3. Опубликовать ветку и открыть PR

```bash
git push -u origin demo/connections-cli

gh pr create --base main --head demo/connections-cli \
  --title "Change connection limits" \
  --body "Set max_connections to 200 for both training profiles."
```

`push` отправляет ветку на GitHub. Ключ `-u` связывает локальную ветку
с удалённой, поэтому следующие отправки можно делать командой `git push`.

`gh pr create` отдельно создаёт предложение о слиянии:
`--head` — ветка с изменением, `--base` — целевая ветка.
Сам по себе `git push` PR не создаёт и ничего не сливает в main.

### 4. Посмотреть результат проверки

```bash
gh pr view
gh pr diff
gh pr checks --watch
```

Последняя команда ждёт завершения проверок. В этом примере первая проверка
должна завершиться ошибкой — ненулевой код команды здесь ожидаем.

В журнале шага Validate proposed configuration будет:

```text
FAIL: db01 (small): max_connections=200; allowed range: 1..100
PASS: db02 (large): max_connections=200; allowed range: 1..300
RESULT: FAIL
```

Список запусков и журнал конкретного запуска тоже доступны из терминала:

```bash
gh run list --branch demo/connections-cli
gh run view RUN_ID --log-failed
```

Вместо `RUN_ID` подставьте номер из списка запусков.
Если удобнее посмотреть PR в браузере, выполните `gh pr view --web`.

### 5. Исправить настройку в той же ветке

В редакторе поменяйте только значение small на 100. Для large оставьте 200.

```bash
git diff
git add config.ini
git commit -m "Use a valid limit for the small profile"
git push
gh pr checks --watch
```

Новый PR не нужен: существующий обновится после отправки коммита в его ветку.
GitHub Actions запустит проверку ещё раз. Теперь оба значения допустимы.

### 6. Слить изменение после проверки

Сначала прочитайте итоговую разницу:

```bash
gh pr diff
gh pr view
```

Когда изменение проверено и его действительно нужно включить в main:

```bash
gh pr merge --merge
```

Это необязательный шаг для демонстрации. Можно оставить PR открытым,
чтобы main сохранил исходные значения для следующего показа.

В данном репозитории main защищён: требуется PR, успешная проверка
`config-check` и актуальность ветки относительно main. Правило распространяется
и на администратора. Одобрение другого человека не требуется, поскольку
это пример для одного аккаунта. В рабочем процессе ревью выполняет коллега.

## Где работает GitHub Actions

В workflow указано `runs-on: ubuntu-latest`. Для этого задания GitHub выделяет
временную среду Ubuntu на своей инфраструктуре. Она получает копию репозитория,
выполняет тесты и проверяет конфигурацию. Наш компьютер и учебные ВМ для этого
не используются. Между заданиями не следует рассчитывать на сохранение её диска.

Запуск происходит при создании и обновлении PR в main, изменении main
или ручном запуске. Обычный push в отдельную ветку без открытого PR
в нашем workflow проверку не запускает.

Те же команды можно выполнить локально, если установлен Python 3:

```bash
python3 -m unittest -v
python3 check_config.py
```

Тесты проверяют, правильно ли работает скрипт, включая отклонение плохих значений.
Поэтому они могут пройти, а следующая проверка самого config.ini — завершиться
ошибкой. Это два разных результата.

## Для каких задач подходит Actions

Actions может выполнять не только короткие проверки. Например:

- проверять YAML, синтаксис Ansible и правила для разных групп серверов;
- запускать тесты приложения с временным PostgreSQL;
- собирать контейнерные образы и публиковать их в реестр;
- после согласования запускать Ansible или другие средства развёртывания;
- выполнять несколько заданий параллельно, например для разных версий PostgreSQL.

Для действий во внутренней сети нужен разрешённый сетевой доступ
или собственный исполнитель — self-hosted runner.
В этом примере он не нужен, как не нужны и секреты доступа к серверам.
Возможности ограничиваются ресурсами исполнителя, временем задания,
правами, сетью и доступными квотами GitHub.

Зелёная проверка подтверждает только заложенные в неё условия.
Она не заменяет проверку смысла изменения и не применяет конфигурацию к БД.
Особенно внимательно проверяйте изменения самого workflow и правил проверки:
автор PR технически может изменить и их.

Рабочие конфигурации и секреты в этот открытый репозиторий не добавляем.
Задания и пояснения в TXT преподаватель выдаёт отдельно.
